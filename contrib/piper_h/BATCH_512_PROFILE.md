# PiPER H 512 场景运行耗时剖析

测量日期：2026-09-29。结论：页面任务的最大开销是 **CPU 串行压缩回放**；物理步内部的最大单项是 **SDF 接触搜索**，但运动学、动力学和约束求解也占有较大比例。优化页面完成时间，应优先处理保存；优化物理吞吐，应优先处理 SDF 搜索，同时关注动力学和约束。

## 测试配置与计时口径

分析对象为运行历史 `abb24fef248b4d188562b21986b8a520`，北京时间 2026-09-29 13:42:11 提交。物体为 60 mm 方块，512 个独立场景，任务长度 12 s，物理步与控制更新均为 2000 Hz，每场景 24000 步，合计 12288000 个环境物理步。两指和物体使用 257³ 稠密 SDF，cell 梯度缓存；40 个 Halton 起点、最多 10 轮主搜索，接触维度 6，求解迭代上限 50，`nconmax=256`、`njmax=1024`。

设备为 RTX 5090 D v2，软件为 MuJoCo 3.13.1、Warp 1.15.0。仓库 HEAD 为 `68a3cb83ae0d5169f7e6246a6467ce23df1711f3`，测量使用当前工作区代码，包括尚未提交的上传、运行统计和批量场景选项修改。

本文区分三种计时，不能混用分母：

- **页面端到端时间**：使用原运行历史的五个阶段计时，包括模型、仿真、验收和保存。
- **物理步循环墙钟时间**：GPU 同步后开始、循环结束后再次同步，包含单步 CUDA graph 提交、状态记录、100 Hz 接触力记录、周期进度同步；不包含 SDF 缓存构建、graph 捕获和最终大数组下载。
- **GPU 物理模块时间**：只计 `mjw.step`，用 CUDA events 包围内部模块；不包含控制目标写入、回放记录和接触力记录。完整轨迹重复三轮，每 100 步采样一次，每轮 240 个样本，按代表步数加权。分别进行仅外层计时和内部插桩计时校准。

## 原任务的端到端时间

| 阶段 | 耗时 | 占总耗时 |
| --- | ---: | ---: |
| 提交配置 | 0.13 s | 0.2% |
| 编译模型 | 3.63 s | 5.4% |
| 生成轨迹 | 0.01 s | <0.1% |
| 运行仿真 | 20.17 s | 29.7% |
| 验收并保存 | 43.86 s | 64.7% |
| 合计 | **67.80 s** | **100%** |

20.17 s 的运行仿真中，物理步循环为 **18.1475 s**，占端到端时间 26.8%；其余约 **2.0208 s** 包含 Warp 模型准备、稠密缓存、数据分配、graph 捕获和最终下载，原任务没有进一步分开这些子项。

物理吞吐约为 **677116 个环境物理步/s**，每个包含 512 场景的批次步平均 **0.7561 ms**。页面 10 Hz 环境步统计是同一物理循环的时间折算，不是额外执行一个环境步骤模块。

## 验收与保存：瓶颈是压缩

保持原配置完整复跑一次，物理步循环 **18.1880 s**、包含准备和下载的运行仿真 **19.6149 s**；512 个场景全部通过完整轨迹验收。记录数组合计 **2954042048 bytes，约 2.95 GB / 2.75 GiB**。

随后用 `cProfile` 分别测量验收和压缩。压缩保持 `save_world_traces` 的数组、顺序及 `np.savez_compressed` 调用，每场景两份 NPZ，但写入 `BytesIO`，从而排除文件创建、磁盘写入和重命名，不重复生成一套大历史文件。

| 复跑后的 CPU 阶段 | 耗时 | 说明 |
| --- | ---: | --- |
| 验收 512 个场景 | 0.907 s | 包含完整步数的状态、接触与搬运指标验收 |
| 内存中压缩全部回放 | **43.418 s** | 1024 次 `np.savez_compressed` |
| 其中 zlib `compress` | **42.040 s** | 占内存压缩耗时 96.8% |
| 其中 zlib `flush` | 0.236 s | 与上一项为不同调用 |
| 其中 CRC32 | 0.325 s | 压缩归档校验 |

即使不写磁盘，压缩仍需约 43 s，与原任务“验收并保存”的 43.86 s 接近，说明本次保存阶段主要由 CPU 压缩消耗决定。以上为另一轮测量，不能通过跨轮相减把磁盘耗时精确算出来。

原任务落盘总量 **1.4827 GB**：512 份状态回放合计 1.2483 GB，512 份接触力回放合计 0.2344 GB。当前 [save_world_traces](grasp_dashboard.py) 在 Python 循环中串行压缩每个场景的两份归档。状态记录为 2000 Hz，接触力记录为 100 Hz，均在物理步循环结束后集中保存。

## GPU 物理步内部的模块分布

下表为三轮内部插桩样本的加权平均，时间为 **512 场景一起推进一个物理步**。各行互斥，总和为 100%；SDF 窄相另列为碰撞内部子项。

| 模块 | 平均批次步耗时 | GPU 物理步占比 |
| --- | ---: | ---: |
| 碰撞检测 | **0.2595 ms** | **33.8%** |
| 运动学与其他动力学 | **0.2101 ms** | **27.4%** |
| 约束求解器 | **0.1519 ms** | **19.8%** |
| 约束构建 | 0.0977 ms | 12.7% |
| 隐式积分 | 0.0442 ms | 5.8% |
| 其他阶段间操作 | 0.0041 ms | 0.5% |
| 合计 | **0.7675 ms** | **100%** |

仅外层计时的 GPU 批次步中位数为 **0.7505 ms**；内部插桩平均相对增加约 **2.3%**。三轮碰撞占比为 33.83%、33.82%、33.79%，结果稳定。表内毫秒值含插桩影响，不应当作为未插桩运行的精确绝对成本。

“运动学与其他动力学”计算为 `fwd_position - collision - make_constraint + fwd_velocity + fwd_actuation + fwd_acceleration`，包括关节与几何变换、惯量相关计算、传动、速度项、驱动力和自由加速度。这样避免将位置阶段内的碰撞、约束重复计入。

### 碰撞检测细分

| 碰撞子项 | 平均批次步耗时 | 占整个 GPU 物理步 |
| --- | ---: | ---: |
| **SDF 窄相接触搜索** | **0.2353 ms** | **30.7%** |
| 其他窄相 | 0.0172 ms | 2.2% |
| NXN 广相筛选 | 0.0054 ms | 0.7% |
| 碰撞阶段其他操作 | 0.0016 ms | 0.2% |

SDF 窄相占碰撞阶段 **90.7%**。这个测量边界覆盖 [_sdf_narrowphase](../../mujoco_warp/_src/collision_sdf.py) 整个 kernel，包括起点生成、梯度与距离查询、回溯搜索、接触构造及写入；**不是单次 SDF 查表耗时**，本次未进一步分离 kernel 内的这些操作。

稠密 SDF 改变了查表方式，但仍保留 40 起点及迭代搜索。进入搜索的起点可能提前退出，不能把迭代上限乘起点数当作实测查询次数。该 kernel 按 `(sdf_initpoints, d.naconmax)` 启动；本次接触总容量为 `512×256=131072`，启动维度为 `40×131072`，约 524 万逻辑线程。大量线程会根据实际候选数提前返回，这个维度不等于实际接触数或查询数。

### 任务阶段差异

时间窗口按当前 12 s 任务长度显示，已修正旧 profiler 使用的 24 s 阶段标签。

| 阶段 | 时间窗口 | GPU 批次步 | SDF 窄相 | SDF 占本阶段物理步 |
| --- | --- | ---: | ---: | ---: |
| 接近 | 0–3 s | 0.6858 ms | 0.1445 ms | 21.1% |
| 夹紧 | 3–4 s | **0.9649 ms** | **0.3707 ms** | **38.4%** |
| 抬升 / 横移 | 4–7 s | 0.7509 ms | 0.2590 ms | 34.5% |
| 下降 / 释放 | 7–9.75 s | 0.8490 ms | 0.3292 ms | 38.8% |
| 退回 / 静置 | 9.75–12 s | 0.7110 ms | 0.1495 ms | 21.0% |

接触搜索成本在夹紧、下降和释放阶段明显增加；当前方块任务的平均分项不能直接推广到复杂上传网格、随机初始姿态或不同容量配置。

## 回放记录和调度对照

相同配置和完整轨迹，保留每步控制提交及物理步，关闭回放记录、接触力记录和周期进度下载，另测三轮。纯步进墙钟为 **17.8673、17.8847、17.8619 s**，中位数 **17.8673 s**。

含记录的完整复跑步进为 18.1880 s，两者相差约 0.32 s；这一对照没有显示回放采样是步进内的主要开销。差值同时包含状态记录、接触统计、接触力采样、进度同步以及重复运行波动，不能单独解释为接触力模块成本。两种运行都使用单步 graph 提交，本次没有测试多步合并提交的收益。

稠密缓存为三个 mesh 共用的模型数据，约 3.01 GiB，不随 512 个场景重复建立。复跑后另外一次暖缓存构建计时为 0.022 s，这不代表冷启动模型编译成本；历史编译模型仍需 3.63 s。

## 优化优先级与实测依据

另取原运行第一个场景的实际两份回放数组，重复编码 32 次，每种方式测三轮取中位数。只测内存归档，不含磁盘；每种方式均验证读回数组逐项完全一致。

| 无损保存方案 | 32 场景样本耗时 | 相对当前速度 | 单场景归档字节数 |
| --- | ---: | ---: | ---: |
| 当前默认压缩，串行 | 2.726 s | 1.00× | 2894400 |
| 当前默认压缩，8 线程 | **0.377 s** | **7.23×** | **2894400** |
| DEFLATE 级别 1，串行 | 1.640 s | 1.66× | 2923523 |
| 不压缩，串行 | 0.030 s | 90.78× | 5777230 |

优先采用有界线程池并行压缩，每个任务独立操作一个场景的文件，保留临时文件加原子替换。小样本下默认压缩参数与归档大小不变、编码快约 7.2 倍；512 个真实文件的端到端收益还需在落盘条件下验证。降低压缩级别可减少约 39.8% 编码时间，归档仅增加约 1.0%；不压缩使数据量约翻倍，内存编码结果不能预测磁盘保存速度。

其次可研究回放降采样保存，在完整物理步上验收后只保存回放所需帧，减少状态数据量、压缩工作及文件读取成本。这是数据记录策略修改，不应同时降低物理更新频率以混淆物理性能对比。

物理吞吐优化优先研究 SDF 距离与梯度联合查询、同一点距离复用及接触起点缓存等搜索成本。即便把物理循环整体耗时全部消除，原页面任务理论上也最多减少约 27%；按当前分项粗略折算，仅消除 SDF 窄相对应端到端约 8% 的量级。该折算忽略模块耦合和插桩差异，仅用于判断优化优先级。

约束构建与求解合计约 32.5%，也值得单独研究。50 是求解迭代上限，求解器使用条件 graph，并不代表每个场景每步固定执行 50 次迭代。接触和约束容量对部分 kernel 的启动规模及缓冲区大小有影响，可在逐步检查容量溢出和完整验收的条件下单独做参数对照。

既有 [Physim 对比报告](PHYSIM_COMPARISON.md) 使用统一 Warp 1.17 环境、多步合并提交并排除回放记录，本次页面使用 Warp 1.15、单步提交且完整记录回放。不能直接拿页面总计 67.80 s 或步进 18.15 s 与该历史 Physim 数值计算引擎速度比。

上述初始剖析仅增加报告和本地测量产物；后续保存优化及落盘验证见下一节。

## 保存优化后的 512 场景落盘验证

同日将 `save_world_traces` 改为最多 8 个线程并行保存独立场景。每个线程共享只读数组视图，无需复制整个批次；继续使用原有 `np.savez_compressed` 默认压缩、目录结构和临时文件加原子替换。单场景直接保存。全部归档完成后才更新完成状态，线程异常会传播到任务失败处理，失败的临时文件会清理。

验收仍逐场景检查完整物理轨迹。本次没有改变物理参数、接触搜索、验收标准、回放采样频率或压缩级别。新增 `metrics.json` 的 `validation_seconds`、`save_seconds`，便于后续单独观察两项成本。

重启服务后，通过实际网页 API 提交与原记录完全相同的配置，运行 `d787cafb4d65419798e0a80a6625d104`，北京时间 14:03:28 开始。结果如下：

| 页面任务阶段 | 原记录 | 优化后记录 |
| --- | ---: | ---: |
| 提交配置 | 0.13 s | 0.12 s |
| 编译模型 | 3.63 s | 3.97 s |
| 生成轨迹 | 0.01 s | 0.01 s |
| 运行仿真 | 20.17 s | 23.62 s |
| **验收并保存** | **43.86 s** | **6.64 s** |
| **总计** | **67.80 s** | **34.36 s** |

验收并保存加速约 **6.61 倍**，耗时减少 **84.9%**。其中验收 **0.877 s**、实际文件保存 **5.760 s**。端到端耗时减少 **49.3%**；这轮运行仿真耗时比原记录高，因此该端到端结果没有假定物理步耗时恒定，保存改动发生在物理循环结束后。

512/512 场景验收通过，生成全部 1024 份 NPZ，没有残留 `.part.npz`。检查场景 1、256、512 的完整状态数组和接触力数组，并通过服务 API 实际渲染场景 1、512 的接触力回放。36 个 dashboard 测试通过，覆盖真实短步 GPU 批次至 1024 场景、并发保存逐项数组及 dtype 一致、原数组不被修改、失败保留已有归档并清理临时文件，以及保存失败时任务不能标记完成。Ruff 检查和格式检查通过。
